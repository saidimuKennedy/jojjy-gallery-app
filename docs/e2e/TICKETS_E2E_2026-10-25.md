## Refund / ticket invalidation

- Ticket-scoped refund: order `9000aabe`, ticket `DC64E7CB`, USD 20 → Paystack
  refund `18839732`, **KES 260,000** (half of the KES 520,000 charge). It later
  settled (`processed`); the ticket became `REFUNDED`, the checked-in ticket
  stayed `CHECKED_IN`, order `PAID/PARTIALLY_REFUNDED`, and tier capacity
  returned 3 → 2 (one unchecked ticket returned).
- While the refund is pending the ticket remains `VALID` and the checked-in
  ticket remains `CHECKED_IN`; the order remains `PAID/SUCCESS`. Paystack is the
  source of truth for settlement.
- Controlled PROCESSED-provider probe:
  - Partial **order** refund → order `PARTIALLY_REFUNDED`, both tickets remain
    `VALID`.
  - Full order refund → order `REFUNDED`, both tickets `REFUNDED`; check-in
    returns `409 REFUNDED` (code cannot be reused).
  - Ticket-scoped full refund → only that ticket `REFUNDED`; the other remains
    `VALID`; order `PARTIALLY_REFUNDED`.
- Refunded tickets are invalidated; their code is never reissued. For an
  unchecked ticket, the refund returns one unit of capacity to the tier so the
  seat can be sold again. A checked-in ticket keeps its capacity consumed (the
  seat was already admitted) even though its code is voided.

## Fixes from this pass

1. Public availability now subtracts `quantityReserved` everywhere (event detail,
   events index, CRM overview, CRM sales). Holds can no longer inflate
   “seats remaining”.
2. `ticketSaleStatus`/checkout entry treat a fully held tier as sold out; the
   checkout modal cannot open with `remaining=0`.
3. Ticket reservation release is claimed per row (`ACTIVE → RELEASED`) so a
   concurrent/duplicate release cannot decrement `quantityReserved` twice.
4. Fulfilment capacity claims respect active reservations even when an order’s
   reservation is missing/expired, preventing oversell.
5. Duplicate ticket-type lines in one checkout are rejected (would otherwise
   create two reservations/ticket lines for one tier).
6. Fulfilment handles multiple reservations for the same ticket type via a queue
   and rejects reservation/order quantity mismatches instead of over-issuing.
7. `reverseCheckIn` uses compare-and-swap on the exact check-in state; concurrent
   reversals cannot create duplicate reversal history or clear a newer scan.
8. Refund invalidation is now refund-scoped:
   - partial order refunds do **not** void tickets;
   - ticket-scoped refunds void only that ticket, and only once its price is
     fully refunded;
   - full order refunds void all tickets.
   Unchecked refunded tickets return their tier capacity once; checked-in
   tickets are voided but keep capacity consumed. Repeats are idempotent.
9. App order views expose refund state (`REFUNDED` / `PARTIALLY_REFUNDED`) so a
   refunded ticket order is not labelled “Payment pending”.

## Guest retrieval and settlement

- Guest checkout now redirects to `/tickets/retrieve?email=…`; the Paystack
  callback appends the reference.
- The retrieve API verifies a pending Paystack reference server-side using the
  same `completeOrderFromPaystackReference` path as the webhook, then returns
  the issued tickets.
- Guest retrieval test: order `ea71a8e8…`, reference + `qa.guest@example.com`
  returned ticket `D05CEACC`; wrong email returned `404`. The guest ticket has
  no `userId`; it is not shown in the signed-in account wallet.
- Paystack test refunds eventually settled asynchronously:
  - product full refund `18839564` → `processed`;
  - product partials `18839590` (KES 52,000) and `18839616` (KES 78,000) →
    `processed`; both product orders became `REFUNDED`, stock returned to 5;
  - ticket refund `18839732` also reached `processed`; one unchecked ticket
    returned capacity (sold 3 → 2), checked-in ticket kept its seat.
- **B9 is resolved in test mode:** test refunds settle asynchronously; do not
  retry a processing refund. Live refund settlement remains B3.

## Residual decisions

- Checked-in tickets keep capacity consumed after a refund; only unused tickets
  return capacity.
- A refund submitted successfully but failing before a provider id exists still
  needs operator attention (no blind resubmit).
- Temporary QA accounts, test product/event, paid orders, tickets, and refunds
  were removed from the local DB after all test refunds reached `PROCESSED`.
  This report remains the reproducible evidence.
